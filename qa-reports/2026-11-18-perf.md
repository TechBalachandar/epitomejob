## 4. Bug found and fixed during this phase: `params.expectedStatuses` does not exist in k6

`coach.js` (and my first draft of `copilot.js`) set
`params.expectedStatuses = [200, 503]`. That key is **not part of k6's
Params** — k6 silently ignores unknown params. Evidence from the stub
run with the old form: checks 100% (64/64) but `http_req_failed`
**88.23% (30/34)** and the `rate<0.01` threshold failed (exit 99) —
every expected 404 counted as a failure. The correct mechanism is
`params.responseCallback = http.expectedStatuses(200, 503)` (k6 docs /
community). After the fix, the same runs show `http_req_failed`
**0.00%** and exit 0 for both `copilot.js` (404s) and `coach.js`
(503s). Both files were updated with a comment documenting the fix and
the evidence. Consequence for the nightly workflow: before this fix,
the coach journey could never pass its threshold while Ollama was down
(which is always in CI) — any past coach FAILs on that threshold were
this bug, not the route.

## 5. Pending on the Mac/staging — exact commands (k6)

Prerequisites: the compose stack up and healthy, and k6 installed.
Auth prerequisite: none manual — every script self-seeds (registers a
fresh unique user and logs in; no fixture user or secret needed).

```bash
# From the repo root (branch kotlin-migration):
docker volume create backend_pgdata || true
docker volume create backend_rustfsdata || true
docker compose up -d --build postgres rustfs backend agent-brain gateway web resume-builder-service
# Wait until all three answer:
#   curl -fsS http://localhost:8080/actuator/health
#   curl -fsS http://localhost:3000/login
#   curl -fsS http://localhost:8000/health

# k6 (Mac, Homebrew): brew install k6
# k6 (CI/Ubuntu, what quester-perf.yml does):
#   curl -fsS https://dl.k6.io/key.gpg | sudo gpg --dearmor -o /usr/share/keyrings/k6-archive-keyring.gpg
#   echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" \
#     | sudo tee /etc/apt/sources.list.d/k6.list
#   sudo apt-get update -qq && sudo apt-get install -y -qq k6

# Base URL is the gateway, exactly like the web BFF uses:
K6_BASE_URL=http://localhost:8080 bash k6/run-all.sh
# Writes one NDJSON file per journey into k6-results/<name>.json plus
# k6-results/status.txt ("<name> PASS|FAIL" per journey). Exits non-zero
# if any journey failed its thresholds. To run one journey:
#   K6_BASE_URL=http://localhost:8080 k6 run --out json=k6-results/copilot.json k6/copilot.js
```

Thresholds to watch (k6 enforces; `scripts/perf-report.py` displays):

| Journey | p95 | Error rate | Checks | Accepted statuses |
|---|---|---|---|---|
| login, profile, jobs, matches, tracker, resume-builder, resume-text, approvals, interviews, sponsor-jobs | < 500 ms | < 1% | > 99% | 200 (201 on creates) |
| coach | < 5000 ms | < 1% | > 99% | 200 or 503 (Ollama down) |
| copilot | < 5000 ms | < 1% | > 99% | 200, or 502 (agent-brain down) |

Watch specifically on the first live run:
- `resume-text`: if setup fails, the fixture PDF did not parse under
  PDFBox (parsed text empty → GET /text returns 400). That is a
  fixture/backend finding, not a script bug.
- `copilot`: a 404 rate > 0 is a REAL failure now — the endpoint exists
  on this branch, so 404 means the route/proxy is broken. A 502 rate
  means agent-brain is down (Ollama). Expect 200s with an `options`
  array.
- `interviews` / `approvals`: both depend on the V3 seeded jobs; an
  empty-jobs failure means the seed migration did not run.
- `approvals`: propose (201) then approve (200, status APPROVED). The
  payload is a JSON *string*, not an object.

## 6. Pending on the Mac/staging — exact commands (Lighthouse)

`lighthouse/lighthouserc.json` currently collects **only**
`http://localhost:3000/login` (3 runs, asserts: performance ≥ 80,
accessibility = 100, best-practices ≥ 80, SEO ≥ 80). The 5 new views are
**not** in the LHCI URL list yet, and they were deliberately not added
here: unauthenticated curl returns the shell with no content, so it is
not established whether LHCI can measure the signed-in views without an
authenticated session — adding the URLs blind would measure a signed-out
shell. Decide on the Mac first (open question), then extend the `url`
array, e.g.:

```json
"url": [
  "http://localhost:3000/login",

  "http://localhost:3000/cover-letter",
  "http://localhost:3000/offers",
  "http://localhost:3000/resume-builder",
  "http://localhost:3000/interviews"
]
```

Chromium installed — the same steps `quester-perf.yml` uses):

```bash

npx -y @lhci/cli autorun --config=lighthouse/lighthouserc.json
```
